# P1.6 Journal / Event Model

**Status:** SPECIFIED — NOT IMPLEMENTED
**Phase:** P1.6
**Depends on:** P1.0 Verification / Cross-System Baseline, P1.1 Authorization / Ownership Boundary, P1.2 Durable Command Lifecycle, P1.3 Error / Failure Semantics, P1.4 Operations State Boundary, P1.5 Backup / Restore Lifecycle
**Scope:** durable event history, audit-event semantics, journal query/read model, retention, and event provenance

## 1. Purpose

Define one durable, queryable, privacy-safe event model for HydraGrow Journal.

P1.6 establishes the semantic contract for what happened, when it happened, which resource it belongs to, what caused it, and how the frontend can retrieve historical events without reconstructing history from current state.

The Journal is historical evidence. It is not current operational state, telemetry storage, the durable command aggregate, or configuration storage.

P1.6 MUST preserve:

- `StationContext` as the frontend identity boundary;
- React Query as the owner of server-backed Journal state;
- `useDeviceStore` as PWM-preference-only;
- `useDeviceSync` as transport/orchestration-only;
- P1.1 authorization and ownership semantics;
- P1.2 durable command lifecycle as the authoritative command aggregate;
- P1.4 operational-state boundaries;
- P1.5 backup semantics, including exclusion of journal/event history from configuration backups.

P1.6 MUST NOT redesign P1.2 command lifecycle, P1.7 API consolidation, P1.8 navigation, P1.9 broad schema unification, or P1.10 observability architecture.

## 2. Problem statement

The current `system_events` infrastructure already persists a broad set of operational, alert, device, dosing, water, calibration, automation, and user-action records. The frontend already presents these records as Journal/System Log and supports filtering, search, acknowledgement, cursor pagination, and CSV export.

The remaining contract gaps are semantic rather than merely visual:

- event identity and provenance are not uniformly defined;
- event categories and levels are not governed by one bounded vocabulary;
- historical events must not be confused with current state;
- command lifecycle events must not become a second command aggregate;
- station-level Journal views need deterministic resource scoping;
- acknowledgement/resolution needs explicit semantics distinct from event occurrence;
- pagination must remain deterministic when many events share timestamps;
- deduplication must not silently erase meaningful repeated events;
- retention must be explicit and observable;
- audit records must remain useful without storing secrets or uncontrolled payloads;
- export must be bounded, authorized, and deterministic;
- historical records must survive current-state changes and backend restart.

P1.6 closes these gaps around the existing event persistence model rather than creating an unrelated second journal database.

## 3. Definitions

### 3.1 Event

An immutable historical fact that an action, observation, state transition, failure, alert, synchronization result, or other defined occurrence happened.

An event records history. It MUST NOT be updated to rewrite the original occurrence.

### 3.2 Journal

The user-facing historical query/read model over authorized events.

Journal ordering, filtering, grouping, and presentation MAY change without changing the underlying event fact.

### 3.3 Audit event

An event describing an actor-initiated or security-sensitive action, including configuration mutation, control action, backup/restore action, pairing, permission change, or other protected operation.

Audit metadata MUST identify the actor/principal and outcome where available, without storing credentials or secrets.

### 3.4 Operational event

An event generated by device/controller/FSM/automation/runtime behavior, such as state transition, actuator action, connectivity change, safety rejection, dosing lifecycle, or synchronization outcome.

### 3.5 Resolution

A separate mutable acknowledgement state associated with an event. Resolution indicates that a human/operator or defined workflow has acknowledged/handled the event; it does not alter the original event fact.

### 3.6 Current state

The latest authoritative state exposed by P1.4 telemetry/state contracts. Current state MUST NOT be reconstructed by replaying Journal events unless a later phase explicitly defines such a projection.

## 4. Canonical event envelope

The persisted event model MUST have a stable canonical representation equivalent to:

```json
{
  "id": 12345,
  "occurred_at": "RFC-3339 timestamp",
  "received_at": "RFC-3339 timestamp",
  "resource": {
    "station_id": "optional station id",
    "device_id": "optional device id",
    "controller_id": "optional controller id"
  },
  "category": "alert | automation | calibration | device | dosing | sensor | system | user_action | water | ...",
  "level": "info | success | warning | error | critical",
  "event_type": "bounded.event.type",
  "title": "human-readable title",
  "message": "human-readable summary",
  "source": "user | controller | sensor | fsm | automation | watchdog | backend | system",
  "actor": {
    "kind": "user | service | device | system | unknown",
    "id": "optional stable actor id"
  },
  "reason_code": "optional bounded reason code",
  "correlation": {
    "trace_id": "optional id",
    "command_id": "optional durable command id",
    "cycle_id": "optional dosing/automation cycle id"
  },
  "metadata": {},
  "resolution": {
    "resolved_at": "optional RFC-3339 timestamp",
    "resolved_by": "optional actor id"
  }
}
```

The exact physical schema MAY reuse the existing `system_events` columns where they already represent these concepts. P1.6 MUST avoid duplicate storage of the same event solely to create a new Journal table.

The current `id`, `device_id`, `level`, `category`, `title`, `message`, `reason`, `metadata`, `timestamp`, `source`, `primary_reason_code`, and `resolved_at` fields are existing persistence primitives. P1.6 defines how those primitives are interpreted and what additional fields are genuinely required.

`occurred_at` and `received_at` MUST be distinguished when the producer can provide both. If only one timestamp exists, its semantic meaning MUST be explicit rather than guessed.

## 5. Event immutability

Once an event occurrence is persisted:

- event identity MUST NOT change;
- occurrence timestamp MUST NOT change;
- source/provenance MUST NOT be rewritten;
- original title/message/reason MUST NOT be edited to change history;
- correlation identifiers MUST remain stable;
- original metadata MUST NOT be silently replaced.

Resolution/acknowledgement is the only ordinary mutable lifecycle attached to an event.

If a later observation contradicts an earlier event, P1.6 MUST append a new event describing the contradiction/correction. It MUST NOT rewrite the earlier record.

Administrative deletion, if ever required, MUST be a separately authorized data-retention operation and MUST NOT be presented as event correction.

## 6. Event identity and ordering

Every persisted event MUST have a unique server-generated identifier.

Journal ordering MUST be deterministic:

1. primary order: `occurred_at` descending;
2. secondary order: server-generated event ID descending.

If the existing integer `timestamp` remains the physical timestamp column, the implementation MUST preserve millisecond precision semantics and use the event ID as a tie-breaker.

Cursor pagination MUST use a stable compound cursor equivalent to:

```text
(before_occurred_at, before_event_id)
```

A timestamp-only cursor is insufficient because multiple events can share the same timestamp.

The same filter + same authorization context + same underlying data MUST produce deterministic page boundaries.

Offset pagination MUST NOT become the canonical Journal pagination mechanism.

## 7. Event taxonomy

P1.6 MUST define a bounded category/event-type vocabulary rather than allowing arbitrary frontend labels to become durable semantics.

Minimum categories:

- `alert`
- `automation`
- `calibration`
- `device`
- `dosing`
- `sensor`
- `system`
- `user_action`
- `water`

Additional categories MAY exist when a concrete domain requires them, but each addition MUST have a documented producer and UI meaning.

Minimum level semantics:

- `info`: informational occurrence;
- `success`: completed operation with positive outcome;
- `warning`: abnormal or degraded condition that did not fail a protected operation;
- `error`: operation/process failure;
- `critical`: safety-critical or urgent condition.

Levels MUST describe event severity, not frontend visual priority.

`event_type` MUST be a bounded machine-readable identifier where stable machine filtering, deduplication, analytics, or audit semantics depend on the event.

## 8. Provenance and actor semantics

Every event MUST identify its producer/source as far as the system can know it.

Allowed source classes MUST remain bounded. At minimum:

- `user`
- `controller`
- `sensor`
- `fsm`
- `automation`
- `watchdog`
- `backend`
- `system`

User/service initiated events MUST carry actor identity when authenticated identity exists.

Service API keys MUST be represented by stable service identity/label where available; the raw key MUST never be persisted in event metadata.

Device/controller-originated events MUST identify the originating resource separately from the target resource when both matter.

P1.6 MUST NOT infer actor identity from mutable UI labels or request payload fields supplied by an untrusted caller.

## 9. Correlation semantics

Events MAY correlate with other durable domains using stable identifiers:

- `command_id` → P1.2 durable command aggregate;
- `cycle_id` → dosing/automation cycle;
- `trace_id` → request/operation correlation when already available;
- resource IDs → station/device/controller/sensor identity.

Correlation MUST be referential metadata, not a second copy of the correlated aggregate.

A Journal query for a command MAY show command lifecycle events, but P1.6 MUST read authoritative command state from P1.2 when command state is required. Journal events alone MUST NOT be used to reconstruct the current command lifecycle.

## 10. Metadata and privacy boundary

Event metadata MUST be bounded, structured JSON where the existing persistence model uses JSONB.

Metadata MUST NOT contain:

- passwords;
- API keys;
- Firebase credentials or tokens;
- MQTT credentials;
- Wi-Fi passwords;
- private cryptographic material;
- session cookies;
- raw authorization headers;
- full backup artifacts;
- unbounded telemetry streams;
- arbitrary request bodies.

Sensitive values MUST be omitted or represented using the existing non-secret marker contract.

Audit metadata SHOULD contain useful fields such as:

```json
{
  "action": "config_update",
  "target": "device_config",
  "result": "success",
  "actor_kind": "user"
}
```

When old/new configuration values are recorded for audit, only non-secret fields MAY be included, and the payload MUST remain bounded.

Logs emitted by the backend MUST never dump the full event metadata payload merely because an event is being persisted or queried.

## 11. Event creation contract

Any operation that creates a durable Journal event MUST:

1. choose a documented event type/category/level;
2. identify the source;
3. attach the correct resource identity;
4. attach authenticated actor identity for user/service operations when available;
5. attach bounded reason code when applicable;
6. attach correlation IDs when available;
7. sanitize metadata before persistence;
8. persist the event through the canonical backend event-writing path.

A successful protected mutation SHOULD write its audit event in the same database transaction as the mutation when atomic auditability is required.

For an operation whose persistence outcome is unknown, the system MUST NOT write a misleading `success` event. Use an explicit unresolved/failure outcome or emit a later reconciliation event according to P1.3 semantics.

Best-effort event logging MAY be used only where loss of the event cannot make the protected operation unauditable. Security-sensitive and configuration-changing operations require stronger persistence semantics.

## 12. Event sources and required coverage

P1.6 MUST define coverage for at least:

### User/security actions

- configuration create/update/delete;
- recipe create/update/activate/deactivate where applicable;
- manual control commands;
- emergency stop;
- device claim/pair/unpair;
- backup export;
- restore validation/apply/result;
- role/permission changes when those operations exist.

### Device/controller operations

- online/offline transitions;
- controller reconnect/disconnect where represented as a durable event;
- reboot/factory reset requests and outcomes;
- OTA lifecycle events;
- controller configuration synchronization result.

### Operational/safety events

- safety rejection;
- safety-critical trip;
- dosing lifecycle events that are intended for Journal history;
- water operations and abnormal water conditions;
- sensor/calibration failures;
- automation execution outcomes;
- important FSM transitions defined by the operational event contract.

The implementation MUST audit existing producers before adding new event writers so duplicate events are not introduced.

## 13. Deduplication

P1.6 MUST distinguish duplicate delivery from repeated real-world occurrence.

An event MAY be deduplicated only when a stable producer-side identity or explicit deduplication key proves that the same occurrence was delivered more than once.

Repeated alerts separated by the documented cooldown MAY remain separate historical events even when the alerting system uses a deduplication window.

The Journal MUST NOT collapse distinct occurrences merely because category/title/message are equal.

If deduplication is required, the durable uniqueness boundary MUST be explicit, for example:

```text
producer + producer_event_id
```

or another documented stable key.

## 14. Resolution / acknowledgement

Acknowledgement MUST NOT mutate the original event occurrence.

The existing `resolved_at` field MAY remain the persisted resolution marker, but P1.6 MUST define:

- `resolved_at = NULL` → unresolved;
- non-null `resolved_at` → resolved/acknowledged;
- reopening clears resolution state only through an authorized operation;
- actor identity for the resolver SHOULD be retained where the schema permits it.

Resolving an event MUST be authorization-checked against the same station/device ownership boundary as reading/updating that event.

A resolution action MAY itself generate an audit event when required for compliance or security-sensitive workflows.

Resolution MUST NOT imply that the underlying device fault has disappeared. The current health/state model remains authoritative for current condition.

## 15. Authorization and isolation

Journal reads MUST reuse P1.1 authorization and ownership checks.

For a device-scoped query:

- authenticated principal must have access to the device;
- events for another device MUST NOT be returned by manipulating query parameters.

For a station-scoped query:

- station membership/ownership MUST be resolved server-side;
- only devices belonging to the authorized station MAY contribute device events;
- orphaned/unowned devices MUST NOT leak into the station Journal.

Filtering parameters MUST narrow an authorized result set; they MUST NOT grant access.

Journal export uses the same authorization boundary as Journal read, with any additional export permission enforced by the existing scope model. P1.6 MUST document the chosen existing scope; it MUST NOT invent a parallel permission system.

## 16. Journal query contract

The canonical query model MUST support:

- explicit station/device context;
- device filter when station scope is selected;
- category filter;
- event type filter where implemented;
- level/severity filter;
- unresolved-only filter;
- search over bounded human-readable fields;
- time range;
- stable cursor pagination.

A query MUST return events only. It MUST NOT embed large telemetry payloads or current device state snapshots.

The response MUST expose enough source identity for the UI to distinguish Station, Device, Controller, Sensor, User, and System-originated events where relevant.

Server-side filtering is authoritative. Frontend filtering MAY refine already-authorized results for presentation but MUST NOT be the only authorization boundary.

## 17. Station Journal aggregation

Station Journal is a read projection over authorized device/station events.

It MUST:

- resolve station membership server-side;
- preserve each event's source device identity;
- use deterministic ordering across devices;
- support device filtering;
- avoid duplicating the same event once per station member;
- handle an empty station with zero events as a valid state.

Station aggregation MUST NOT copy every device event into a second station event table solely for UI convenience.

## 18. Export contract

Journal export MAY produce CSV and/or JSON using the same authorized query semantics as the Journal UI.

Export MUST:

- apply server-side authorization;
- apply explicit filters and time range;
- use deterministic ordering;
- include event ID, timestamp, resource identity, category, level, event type where available, source, title, message, and bounded audit metadata where permitted;
- exclude secrets and raw credentials;
- enforce a bounded maximum result size or explicit export job mechanism if the result exceeds synchronous limits.

P1.6 MUST NOT turn Journal export into a generic database dump.

Backup artifacts from P1.5 MUST continue to exclude Journal/event history.

## 19. Retention and lifecycle

Event retention MUST be explicit per event class.

The existing 90-day `system_events` retention is the starting baseline and MUST NOT silently change during P1.6.

Before implementation changes retention, the project MUST classify events into at least:

- operational history;
- safety/security audit;
- compliance-required history, if applicable.

Retention jobs MUST:

- delete/archive only records older than the configured retention boundary;
- be idempotent;
- run in bounded batches for large tables;
- emit operational metrics/logs about deletion without logging payload contents;
- avoid blocking normal Journal queries for an unbounded transaction duration.

If an event class requires longer retention, it MUST have an explicit policy and storage decision rather than being accidentally exempt from cleanup.

P1.6 MUST NOT introduce an external archival platform unless the repository already has an authoritative integration and the spec is amended accordingly.

## 20. Backfill and migration

Existing `system_events` rows are historical data and MUST NOT be rewritten merely to make the new UI prettier.

If new required columns are introduced:

1. define deterministic defaults for historical rows;
2. preserve original timestamps and IDs;
3. identify unknown provenance explicitly as `unknown` rather than inventing an actor/source;
4. do not infer event types from free-form text when the inference is ambiguous;
5. keep a migration count and validation report.

Historical command lifecycle events MUST NOT be promoted to authoritative P1.2 command state by inference.

A migration MUST be reversible at the schema level where practical, but event history itself MUST remain append-only from the application semantics perspective.

## 21. Failure semantics

Event persistence failures MUST be classified according to operation criticality.

For protected mutations where audit persistence is part of the atomic contract:

- mutation + required audit event commit together;
- audit insert failure rolls back the protected mutation.

For telemetry/diagnostic events where event loss does not invalidate the operation:

- the producer MAY continue the operation;
- failure MUST be observable through existing diagnostics/metrics;
- the event MUST NOT be reported to the user as durably recorded if persistence failed.

Journal query failures MUST return an explicit error state, not an empty success result.

Retention failures MUST NOT delete partial ranges while claiming full completion.

## 22. Frontend Journal architecture

The frontend MUST use `StationContext` as the selected station/device identity boundary.

Journal server state MUST be owned by React Query.

`useDeviceStore` MUST NOT receive event history, pagination state, filters, acknowledgement state, or Journal cache.

`useDeviceSync` MUST NOT become the Journal transport layer.

The Journal UI SHOULD support:

- station context header;
- device filter;
- category/level filters;
- unresolved filter;
- search;
- deterministic chronological display;
- load-more/infinite cursor pagination;
- event detail drawer;
- acknowledgement/resolution where authorized;
- CSV export;
- loading, empty, offline, and error states.

The UI MUST distinguish:

- event occurrence;
- current device state;
- event resolution.

A resolved historical event MUST NOT be displayed as proof that the current device is healthy.

## 23. API boundary

P1.6 MAY refine existing Journal endpoints and add narrowly scoped event query/export operations.

Minimum logical operations:

- list authorized events;
- acknowledge/resolve one event;
- export authorized events.

API consolidation is P1.7. Therefore P1.6 MUST NOT reorganize the entire API namespace, merge unrelated endpoints, or redesign route conventions outside the Journal/event domain.

Existing endpoint compatibility SHOULD be preserved unless a concrete security or correctness defect requires a versioned change.

## 24. Observability boundary

P1.6 may add bounded counters needed to operate the Journal lifecycle, such as:

- event write failures;
- query failures;
- retention failures;
- export failures;
- deduplication count.

P1.6 MUST NOT perform the broad observability redesign reserved for P1.10.

Metrics labels MUST remain bounded. Device IDs, user IDs, event messages, and arbitrary metadata MUST NOT become unbounded metric labels.

## 25. Testing requirements

### 25.1 Shared/domain tests

- canonical event serialization;
- bounded category/level/event-type validation;
- metadata secret sanitization;
- timestamp semantics;
- stable event identity;
- correlation fields;
- deterministic ordering.

### 25.2 Backend tests

- authenticated device Journal read;
- station aggregation and device isolation;
- cross-owner rejection;
- category/level/search/time filters;
- unresolved filtering;
- compound cursor pagination with equal timestamps;
- event immutability;
- acknowledgement authorization;
- audit actor/source metadata;
- command correlation without replacing P1.2 state;
- duplicate delivery handling;
- protected mutation + audit atomicity;
- query failure not returned as empty data;
- export authorization and secret exclusion;
- retention boundary and bounded cleanup;
- historical migration/default semantics.

### 25.3 Frontend tests

- StationContext drives Journal scope;
- changing station/device invalidates Journal query cache;
- cursor load-more does not duplicate events;
- equal timestamps preserve deterministic order;
- filters map to server query semantics;
- unresolved filter uses resolution state;
- acknowledgement refreshes only relevant React Query state;
- unauthorized/failed acknowledgement is surfaced as an error;
- event detail does not imply current health;
- export failure and empty-result states;
- no Journal state enters `useDeviceStore`.

### 25.4 Runtime tests

Against real PostgreSQL:

1. insert two devices with interleaved event timestamps;
2. query station Journal and verify deterministic global ordering;
3. use compound cursor across equal timestamps;
4. verify cross-owner isolation;
5. acknowledge one event and verify only resolution state changes;
6. verify original event fields remain unchanged;
7. execute a protected mutation with injected audit failure and verify atomic rollback where required;
8. execute retention cleanup against expired fixtures and verify bounded deletion;
9. restart backend and verify historical events remain queryable.

MQTT/controller runtime MAY generate source events, but P1.6 MUST verify persistence semantics independently of live controller availability.

## 26. Acceptance criteria

- **AC-1:** Every persisted Journal event has stable identity, resource identity, timestamp semantics, category, level, source, and bounded content.
- **AC-2:** Event history is append-only; occurrence facts cannot be rewritten through normal application paths.
- **AC-3:** Resolution/acknowledgement is separate from the immutable event occurrence.
- **AC-4:** Journal ordering is deterministic, including events sharing the same timestamp.
- **AC-5:** Cursor pagination cannot skip or duplicate events when timestamps collide.
- **AC-6:** Station Journal aggregates only authorized station resources and preserves source-device identity.
- **AC-7:** Cross-owner and unauthorized event reads/updates/exports are denied server-side.
- **AC-8:** User/service/device provenance is explicit and never inferred from untrusted payload labels.
- **AC-9:** Event metadata cannot persist passwords, tokens, credentials, private keys, session material, backup artifacts, or unbounded payloads.
- **AC-10:** P1.2 command lifecycle remains authoritative; Journal correlation never becomes a second command aggregate.
- **AC-11:** Required audit events are persisted atomically with protected mutations where the operation contract requires atomic auditability.
- **AC-12:** Journal query/export failures are distinguishable from valid empty results.
- **AC-13:** Retention is explicit, bounded, idempotent, and does not silently alter the existing 90-day baseline during initial implementation.
- **AC-14:** Existing historical events remain queryable after backend restart and are not rewritten solely for presentation.
- **AC-15:** Frontend Journal state is owned by React Query and scoped by `StationContext`; `useDeviceStore` remains PWM-only and `useDeviceSync` remains transport/orchestration-only.
- **AC-16:** Runtime PostgreSQL verification demonstrates station aggregation, deterministic cursor pagination, authorization isolation, acknowledgement semantics, and retention behavior.
- **AC-17:** P1.6 does not redesign P1.1 authorization, P1.2 command lifecycle, P1.4 operational state, P1.5 backup/restore, P1.7 API consolidation, P1.8 navigation, P1.9 broad schema cleanup, or P1.10 observability.

## 27. Non-goals

P1.6 does not implement:

- current operational-state storage;
- telemetry/time-series storage;
- durable command aggregate redesign;
- configuration storage;
- backup/restore of Journal history;
- PostgreSQL physical backup/PITR;
- user/account migration;
- credential or secret storage;
- a new authentication/permission system;
- a new external log/archival platform;
- full-text search infrastructure unless current query performance proves it necessary;
- P1.7 API consolidation;
- P1.8 navigation redesign;
- P1.9 broad schema unification;
- P1.10 observability redesign.

## 28. Implementation order

Implementation MUST proceed in this order:

1. audit existing `system_events` producers, consumers, schema, retention, and frontend query paths;
2. freeze the canonical event vocabulary and provenance contract;
3. add only schema fields proven necessary;
4. implement canonical event-write/sanitization helpers;
5. enforce immutable event semantics and separate resolution mutation;
6. implement deterministic compound-cursor queries;
7. enforce station/device authorization and isolation;
8. complete protected-operation audit coverage;
9. implement bounded export and retention behavior;
10. align frontend Journal queries with `StationContext` + React Query;
11. run unit/integration/runtime verification;
12. create P1.6 evidence only from fresh implementation results.

No later-phase semantics may be pulled into P1.6 merely because the implementation touches a shared event path.

- verification timestamp;
